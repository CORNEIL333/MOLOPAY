# Inventaire cryptographique (SEC-CRY-006)

> Tenu à jour **et vérifié** : `tools/crypto-inventory.test.ts` (lancé par `pnpm test`) échoue si un emplacement du code de production emploie un algorithme sans figurer ici, si une ligne cite un emplacement qui ne l'emploie plus, ou si un algorithme faible ou non inventorié (MD5, SHA-1, RSA, PBKDF2, scrypt, 3DES, chiffrement autre qu'AES-256-GCM) apparaît. Toute modification de ce tableau passe donc avec le code qui la justifie.
>
> Périmètre : code de production du dépôt (API, clients web et mobile, paquets, outils dont le vérificateur Rust, migrations SQL). Hors dépôt et donc hors de ce contrôle : TLS des hébergeurs (ADR-0004), chiffrement au repos du fournisseur de base de données, HSM des clés de signature en production (SEC-CRY-003, D5). L'aléa cryptographique est contrôlé à part (SEC-CRY-005, `tools/crypto-randomness.test.ts`).
>
> Colonne « Post-quantique » : **Conservé** — algorithme symétrique ou de hachage, dont la sécurité n'est que réduite de moitié par l'algorithme de Grover (≥ 128 bits ici) ; **À migrer** — signature à courbe elliptique, cassée par l'algorithme de Shor sur un ordinateur quantique suffisant. Cibles normalisées : ML-DSA (FIPS 204) ou SLH-DSA (FIPS 205), dès que le HSM, les navigateurs (WebAuthn) et les témoins d'ancrage les acceptent. Les formats signés portent déjà un identifiant de clé (`key_id`) ou d'algorithme, ce qui permet une double signature pendant la transition.
